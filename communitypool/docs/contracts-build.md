# CommunityPool contract build: canonical toolchain, artifact boundary, V1 provenance

This document is the source of truth for how the Solidity in `src/` is
compiled into the JSON artifacts under `lib/onchain/`, and for which of those
artifacts production actually deploys. The canonical build was established in
Phase 2.0 (2026-09-06); the V1/V2 artifact boundary in Phase 2.1.

## Artifact / version boundary

| File | Source | Regenerated by | Used by production deployment |
| --- | --- | --- | --- |
| `lib/onchain/community-pool-v1-artifact.json` | Phase 2.0 canonical build of V1 `CommunityPool.sol` | **never** (frozen) | no – **not deployed since Phase 2.8**; still the ABI used to read and drive existing V1 pools |
| `lib/onchain/community-pool-v2-artifact.json` | current `src/CommunityPool.sol` (ProtocolConfig-aware; oracle-hardened since Phase 2.6) | `scripts/sync-contract-artifact.mjs` | **yes** – `deployCommunityPool()` in `lib/onchain/community-pool.ts` deploys this |
| `lib/onchain/protocol-config-artifact.json` | `src/ProtocolConfig.sol` | `scripts/sync-contract-artifact.mjs` | no – one shared instance per chain, deployed manually |

Frozen V1 creation bytecode keccak256:
`0xf564efc7c38adc4016e2e09b431d33797f597d4e0fb174bd818bebafb4060c98`.
`scripts/check-frozen-v1-artifact.mjs` (npm `contracts:check-v1-frozen`, run
in the CI node job, and mirrored by
`test/security/contract-artifact-boundary.test.ts`) fails if that hash
changes, if the V1 ABI gains V2 members, if the deploy helper stops deploying
V2, or if it ever hands the frozen V1 artifact to a `ContractFactory` again.
Changing the pinned hash is an explicit, review-visible statement that
production deploys different bytecode.

V1 remains in the tree permanently: pools deployed before Phase 2.8 are live
user contracts with real balances, and the app must keep reading and driving
them. V2 keeps every V1 function with identical selectors, so one ABI serves
both generations for fund and withdraw; only the constructor and the
fee-related views differ.

The V2 artifact was promoted from its `*-candidate-*` filenames in Phase 2.8
with `git mv`, so the bytes are unchanged. Its creation-bytecode keccak256 is
`0x65b585a164c956282c7efc27775926b54fbcc58387e3fea442e1fcff3db7181f` and the
runtime hash is
`0x86f70dd4b6e8557328bbc73de173587b197ff9b2740bddfe0ec80e992f8d6938` — the
same bytecode the Phase 2.7 mainnet canary validated (see
`docs/deployment/phase-2-7-mainnet-canary.md`).

## Canonical build

| Input | Pinned value | Where |
| --- | --- | --- |
| Solidity compiler | `0.8.26+commit.8a97fa7a` | `foundry.toml` `solc_version`, `auto_detect_solc = false` |
| EVM target | `cancun` | `foundry.toml` `evm_version` |
| Optimizer | enabled, 200 runs | `foundry.toml` |
| `via_ir` | `false` | `foundry.toml` |
| Metadata | `bytecode_hash = "ipfs"`, `cbor_metadata = true` | `foundry.toml` |
| Remappings | the four explicit entries in `foundry.toml`; `auto_detect_remappings = false` | `foundry.toml` |
| OpenZeppelin | git submodule `lib/openzeppelin-contracts` at tag `v5.6.1` | `.gitmodules` pointer + `foundry.lock` |
| Chainlink, forge-std, foundry-devops | submodule pointers as committed | `foundry.lock` |
| Foundry (CI) | `v1.8.1` via `foundry-rs/foundry-toolchain` | `.github/workflows/ci.yml` |
| Formatting | `forge fmt --check` | CI contracts job |
| Artifact generation | `forge clean && forge build && node scripts/sync-contract-artifact.mjs` | `scripts/sync-contract-artifact.mjs` |

Why each pin exists:

- **Explicit remappings only.** Foundry auto-discovers remappings from every
  directory under `lib/`, including nested submodules and leftover untracked
  checkouts. The full remapping list is part of the solc metadata JSON, whose
  IPFS hash is embedded in the last 53 bytes of the bytecode. With
  auto-detection on, the *same source and compiler* produced different
  bytecode depending on which directories happened to exist on disk.
- **`evm_version` pinned.** solc 0.8.26 defaults to cancun, but a future
  Foundry or solc bump must not be able to change codegen silently.
- **Foundry pinned in CI.** Foundry 1.5.1 and 1.8.1 produced identical
  artifacts with explicit remappings; the toolchain is pinned and bumped
  deliberately.
- **Settings asserted at artifact time.** The sync script reads the compiler
  settings recorded in `forge-out` and refuses to write or check an artifact
  produced with a different compiler, EVM target, optimizer, remapping set,
  compilation target, or linked libraries.

Reproducing locally:

```bash
cd communitypool
git submodule update --init --recursive
forge fmt --check
forge clean && forge build --sizes
node scripts/sync-contract-artifact.mjs           # regenerate the two candidates
git diff --exit-code -- lib/onchain/community-pool-v2-artifact.json \
                        lib/onchain/protocol-config-artifact.json
node scripts/sync-contract-artifact.mjs --check   # local equivalent (do not run right after regenerate)
npm run contracts:check-v1-frozen                 # frozen V1 guard
```

## CI integrity gate

The `contracts` job runs, in order: checkout with submodules, pinned Foundry,
`forge fmt --check`, `forge clean`, `forge build --sizes`, `forge test -vvv`,
regenerate the candidate artifacts, then `git diff --exit-code` on both
candidate files. The diff is against the files committed at the SHA under
test, so the check is independent of the regeneration step. The `node` job
runs the frozen V1 guard. The pipeline that existed before Phase 2.0
regenerated the artifact and then ran `--check` against the file it had just
written, which could never fail.

## V1 provenance (pools deployed before Phase 2)

Facts established read-only in Phase 2.0:

- The original V1 artifact (creation bytecode keccak
  `0xba3a946b29d13e94ff71502371d46778235ce342f6250134b0dd1bbafc534f44`) is
  byte-for-byte the creation code of both mainnet V1 pools,
  `0x0b4DfD735680B6d3d2c0c9bda23A80f5E15A47c0` and
  `0xb740dFB3F3C93bc33e8AAF76B205E91CCdeAB767` (chain 1, blocks 25043443 and
  25043446, 2026-05-07). Their runtime code, with the four immutables
  (`minimumUsd`, `expiresAt`, `deployer`, `i_ethUsdFeed`) normalised using the
  compiler's `immutableReferences`, equals the runtime template of a clean
  build against OpenZeppelin v5.5.0 through v5.7.0, and the runtime CBOR
  trailer equals the artifact's.
- The artifact's **logic** bytecode is reproduced exactly by solc 0.8.26,
  optimizer 200 runs, cancun, with OpenZeppelin at any revision from v5.5.0
  (2025-10-31) through master as of 2026-04-12. It is **not** reproduced by
  the OpenZeppelin v5.0.2 revision the submodule pointed at before Phase 2.0.
- The artifact's **metadata hash** (last 53 bytes) was not reproduced by any
  evidence-driven candidate; the remaining unknown is the exact auto-detected
  remapping list on the developer's machine in April 2026.

The Phase 2.0 canonical build produced the frozen V1 artifact now in the
repository (keccak `0xf564efc7…0c98`): same ABI and executable logic as the
mainnet pools, different metadata trailer. Existing mainnet pools are immutable
and unaffected by anything in this repository.

## Contract documentation

- V1: the two immutable production pools above and every pool deployed by the
  production app today. No protocol fee; 100% of every contribution stays in
  the pool.
- V2 candidate: `src/CommunityPool.sol` with an immutable reference to the
  shared `ProtocolConfig`, read live via `getProtocolFeeConfig()`, and, since
  Phase 2.3–2.4, protocol-fee collection on `fund` / `fundERC20` (fee deducted
  from the gross contribution, capped at 3%, floor-rounded, sent to the
  configured recipient; see `docs/protocol-config.md`). Withdrawal and
  ownership code is identical to V1. Not deployed, not active in production.
- ProtocolConfig: see `docs/protocol-config.md` (admin role, fee recipient,
  0–300 bps range, two-step admin handoff, no custody authority).
